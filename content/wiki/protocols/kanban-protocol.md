# 📌 Kanban 协议 — 看板工作流

> 基于看板方法的任务管理协议，实现任务的可视化、有序化和持续流动。

## 概述

Kanban 协议定义了从任务创建到完成的完整工作流程。通过看板列（Columns）和 WIP 限制，确保工作有序进行，避免多任务并行导致的效率下降。

---

## 看板列定义

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│  📥 待办  │→│ 📋 进行中 │→│ 👀 待审查 │→│ ✅ 已完成 │→│ 📦 归档   │
│  Backlog │  │  In Progress │ Review │  │  Done    │  │  Archive │
└──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘
```

| 列名 | 含义 | WIP 限制 |
|------|------|----------|
| 📥 待办 (Backlog) | 已识别但未开始的任务 | 无限制 |
| 📋 进行中 (In Progress) | 当前正在处理 | **3** |
| 👀 待审查 (Review) | 完成待验证 | 5 |
| ✅ 已完成 (Done) | 已验证完成 | 无限制 |
| 📦 归档 (Archive) | 已归档的历史任务 | 无限制 |

## 任务生命周期

### 步骤一：任务创建

```
1. 识别任务来源（用户请求 / 定时任务 / 系统事件）
2. 创建任务卡片，包含：
   - 标题：简洁明确
   - 描述：详细说明
   - 优先级：P0（紧急）/ P1（重要）/ P2（普通）/ P3（低优先）
   - 标签：项目标签 + 类型标签
   - 预估工作量：S / M / L / XL
3. 放入 📥 待办列
```

**任务卡片模板：**
```markdown
## [P1] 任务标题

**项目：** [[project-name]]
**类型：** 研究 / 开发 / 文档 / 运维
**工作量：** M（约 2 小时）
**截止日期：** 2026-06-10

### 描述
任务的详细说明...

### 验收标准
- [ ] 条件 1
- [ ] 条件 2

### 依赖
- [[其他任务]]
```

### 步骤二：任务拆分

大型任务需要拆分为可执行的子任务：

```
规则：
1. 单个任务工作量不超过 L（约 4 小时）
2. 每个子任务应有明确的完成标准
3. 子任务间尽量减少依赖
4. 保持子任务粒度一致
```

**拆分示例：**
```
原始任务：[L] 分析鸽子基因组数据
  ├── [M] 数据预处理与质控
  ├── [M] 核心基因组构建
  ├── [S] cgSNP 位点鉴定
  ├── [S] 系统发育分析
  └── [S] 结果可视化与报告
```

### 步骤三：任务执行

```
1. 从 📥 待办中选择最高优先级任务
2. 检查 WIP 限制（进行中 ≤ 3）
3. 移动任务到 📋 进行中
4. 执行任务，记录进展
5. 完成后移动到 👀 待审查
```

### 步骤四：任务审查

```
1. 对照验收标准检查完成质量
2. 如有问题，退回 📋 进行中
3. 如通过，移动到 ✅ 已完成
4. 记录实际工作量和经验教训
```

### 步骤五：归档

```
1. 每周整理 ✅ 已完成列
2. 超过 7 天的任务移入 📦 归档
3. 归档任务保留用于回顾和统计
```

---

## 优先级规则

| 优先级 | 含义 | 响应时间 |
|--------|------|----------|
| P0 | 🔴 紧急：阻塞性问题 | 立即处理 |
| P1 | 🟠 重要：有明确截止日期 | 1-2 天内 |
| P2 | 🟡 普通：常规任务 | 1 周内 |
| P3 | 🟢 低优：改进类任务 | 按排期 |

---

## WIP 限制的意义

> **WIP（Work In Progress）限制**是看板方法的核心。

- **为什么限制为 3？** 人类/Agent 并行处理能力有限，超过 3 个任务会导致频繁切换、质量下降
- **满了怎么办？** 优先完成进行中的任务，而非启动新任务
- **紧急任务怎么办？** P0 任务可以临时突破 WIP 限制，但需尽快收敛

---

## 看板维护

- **每日**：检查进行中任务状态
- **每周**：清理已完成列，归档旧任务
- **每月**：回顾任务统计，优化工作流
